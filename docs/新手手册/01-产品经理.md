# 新手手册 · 01 产品经理（product-manager）

> 这一棒把「我有个想法」变成一份别人能照着做、能判对错的 PRD。
> 不会写产品文档也能用，但有三条规矩必须守，否则后面八棒全部白干。

---

## 一、这一棒是干什么的

你是流水线第一棒。你的唯一产出是一份 `01-prd.md`。

它不写代码、不挑技术栈、不做界面图。它只回答四个问题：

1. 给谁做？
2. 解决他们什么麻烦？
3. 这一期做哪些功能，不做哪些？
4. 做完怎么算成功——能不能用一句话判定"过了"还是"没过"？

**如果这四个问题里有任何一个答不上来，后面九棒做得再漂亮，做出来的也是错的东西。**

---

## 二、为什么非得有这一棒

不用它，你会遇到下面这些事——都不是假设，是用 AI 写项目最典型的翻车方式：

| 不做这一步 | 后面会怎样 |
|---|---|
| 需求只在对话里说过 | 第三棒画原型时，AI 忘掉了两小时前的约定，画出你没提过的页面 |
| 没写"本期不做什么" | 开发阶段功能越加越多，最后交付延期，还说不清是谁加的 |
| 验收标准写成"界面要友好" | 做完你也说不清算不算完成，只能凭感觉验收 |
| 没写成功指标 | 上线后没人知道这次做的东西有没有用 |

一句话：**PRD 不是给领导看的文档，是给下游九棒的输入。**写不清楚，下游只能猜。

---

## 三、什么时候该用，什么时候别用

**该用**：

- 你决定要做这个功能了，需要一个能评审的版本；
- 你要把一段口头需求交给 AI 去实现，希望它别跑偏；
- 你手上有个粗糙的方案，想让人挑毛病。

**别用**：

- 你还在纠结要不要做 → 先聊，聊定了再来；
- 你已经有 PRD，只想改两句话 → 直接改，不必重跑一遍流程；
- 你只想让它赶紧写代码 → 那就别用这条流水线，它天生慢。

技能自己在第 0 步会拦你：如果判断你只是在头脑风暴，它会先问一句"你是要现在产出可评审的 PRD，还是只是聊聊"。这句话不是客套，是门禁。

---

## 四、它只写「要什么」，不写「怎么做」

这是这一棒最容易越界的地方，也是它和第七棒（开发）的分界线。

| 它写（要求） | 它不写（方案） |
|---|---|
| 密码不得明文存储 | 用 bcrypt 还是 argon2 |
| 列表 2 秒内返回 | 用 Redis 缓存还是加索引 |
| 敏感操作需二次确认 | 弹窗还是短信验证码 |
| 支持手机浏览器访问 | 用 Vue 还是 React |

判断口诀：**写出来是"系统应该做到什么"，归你；写出来是"代码应该怎么敲"，归开发。**

拿不准的时候，写成一条可验证的要求，不要写技术名词。写了技术名词，第二棒评审会当成越界打回。

---

## 五、具体怎么做（五步）

### 第 1 步：让它先盘点缺口

打开 `product-manager/` 这个技能，直接说：

```
按 product-manager 的流程，我要做一个「待办清单」工具，帮我出 01-prd.md
```

它会对照模板十节逐格盘点，缺哪格问哪格。**每轮最多问 3 个问题，最多问 3 轮。**

### 第 2 步：认真回答前 3 轮

它最优先问的是这五件事，你最好一次说全：

1. 为谁做（角色，不要写"用户"）
2. 解决什么痛点（具体场景，不要写"提升效率"）
3. 成功指标（可量化，如"新用户 3 分钟内建完第一条清单"）
4. 有没有时间 / 合规约束
5. 本期明确不做什么

答不上来的就说"不知道，你先按合理假设写"。满 3 轮后它不再追问，会把假设标成「假设待确认」写进文档——**这不是它偷懒，是防止无限期问下去。**

### 第 3 步：看它写出来的东西

产出固定叫 `01-prd.md`，十节标题一个字都不能改（脚本按字串硬匹配）：

```
1. 背景与目标        6. 非功能需求
2. 目标用户与场景    7. 范围边界
3. 用户故事          8. 验收标准
4. 功能需求清单      9. 依赖
5. 业务流程         10. 里程碑
```

功能需求编号 `FR-01`、`FR-02`，标 P0 / P1 / P2。验收标准用 Given / When / Then 写。

### 第 4 步：跑校验

```bash
python product-manager/scripts/check_prd.py 01-prd.md
```

退出码 0 才算交稿。见下一节。

### 第 5 步：交给第二棒

```
按 requirement-reviewer 的流程，评审 01-prd.md
```

评审会给 YES 或 NO。NO 就回来改，**最多被打回 2 次**。

---

## 六、怎么知道做完了

只认退出码，不认自我感觉：

```bash
python product-manager/scripts/check_prd.py 01-prd.md; echo "EXIT=$?"
```

| 退出码 | 含义 | 你该做什么 |
|---|---|---|
| 0 | 通过 | 交稿，进第二棒 |
| 1 | 缺章节 | 按模板补齐缺的那节，重跑 |
| 2 | 有占位残留 | 把 `[ ]`、`【 】`、`< >` 里的东西换成真内容，重跑 |
| 3 | 路径不对 | 检查文件是不是叫 `01-prd.md`、在不在当前目录 |

⚠️ 注意：`python xxx.py | tail -5` 这种写法取到的是 `tail` 的退出码，永远 0。**必须先重定向再取 `$?`**，否则你会以为自己通过了。

---

## 七、新手最常犯的五个错

1. **验收标准写成形容词**。"界面友好""响应流畅"——这种写完，第八棒测试无从下手，它会判你不合格。写成"点击保存后 1 秒内出现成功提示"。
2. **用方括号留空**。`【待补充】` 会被校验器判为占位残留，退 2。要留就用普通文字写「假设待确认：目标用户以学生为主」。
3. **在 PRD 里挑技术栈**。"用 PostgreSQL 存数据"——这属于第五棒和第七棒的事，写在这里会被第二棒打回。
4. **没写"本期不做什么"**。这一节看起来最没用，实际是后面挡需求蔓延的唯一依据。
5. **一路改到退 0 为止**。同一份产物连续 3 次失败项相同，就该停下来出阻塞报告，而不是把脚本改宽。

---

## 八、它做不到什么

- **不判断值不值得做**。它只追问到"边界清楚"，商业上要不要做仍是你的判断。
- **不替你补业务知识**。"目标用户是 25 岁女性"这种信息，它编不出来，只能标假设。
- **不保证下游一定做对**。它保证交出去的东西是清楚的，不保证开发不出 bug。
- **不适合非产品类任务**。写论文、做数据分析、修一个已有 bug，用不上这一棒。

---

## 九、记住三句话

1. 十节标题不能改，改一个字校验就挂。
2. 只写"要什么"，不写"怎么做"。
3. 退出码 0 才能交给下一棒，而且取退出码别用管道。
