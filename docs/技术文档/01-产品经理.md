# 技术文档 · 01 产品经理（product-manager）

**版本** 1.5.3 ｜ **阶段** 1/10 ｜ **上游** 业务方口头想法 ｜ **下游** requirement-reviewer ｜ **运行时依赖** 无（纯文本撰写，不执行代码）

---

## 1. 定位

流水线第一棒。把非结构化的口头诉求收敛成一份机器可部分校验、下游九棒可直接引用的 PRD。

它不产出代码、不产出设计图、不做技术选型。**它的价值不在写了什么，而在砍掉了什么**——把"本期不做"写死，是后面所有棒次能收敛的前提。

---

## 2. 输入契约

| 项 | 要求 |
|---|---|
| 触发条件 | 用户明确表达"要做/出 PRD"，而非头脑风暴 |
| 必需前置 | 无（它是第一棒，唯一无上游产物的棒次） |
| 信息完整度 | 允许不完整，但每格缺口必须显式标注 |

**缺口的三种合法处置**（顺序不可颠倒）：

1. 追问——每轮 ≤3 问，累计 ≤3 轮；
2. 满 3 轮或用户说"你先写"→ 基于假设补全，正文注明「假设待确认：内容」；
3. 拿不准是否要问业务方的 → 汇总进「待业务方确认」清单。

**明确禁止**：用 `[ ]`、`【 】`、`< >` 包裹待确认内容。校验器判为占位残留，退 2，不可交付。

---

## 3. 输出契约

- **文件名**：`01-prd.md`（固定，`validate_pipeline.py` 校验此名）
- **十节标题**（字串硬匹配，一字不可改）：

```
背景与目标 / 目标用户与场景 / 用户故事 / 功能需求清单 / 业务流程
/ 非功能需求 / 范围边界 / 验收标准 / 依赖 / 里程碑
```

- **编号规约**：功能 `FR-01…` 标 P0/P1/P2；非功能 `NFR-01…`；风险 `RISK-01…`。
  带稳定编号的作用：下游第七棒在 README 里回写该编号即可通过非功能落实校验，不必逐字抄条目。无编号时校验退化为「前 8 字符锚 + 实词重合度」，语义正确的转述仍可通过。
- **验收标准形制**：Given / When / Then，禁主观形容词。

---

## 4. 校验器行为（`scripts/check_prd.py`）

**判定逻辑**（按源码顺序）：

1. 文件不存在 → 3
2. 十节标题字串缺失 → 记 FAIL
3. 占位符命中（`[...]{2,}` 除 `[^1]` 脚注 / `【...】`；尖括号先剥离自动链接、HTML 标签、泛型后再生效）→ 记 WARN
4. `待补充|TODO|待写|TBD` 命中 → 记 WARN
5. 有 FAIL → 1；仅有 WARN → 2；否则 → 0

**退出码**：`0` 通过 ｜ `1` 缺章节 ｜ `2` 占位/TODO 残留（缺参数也是 2，与业务警告共用） ｜ `3` 路径不存在。

**已做的防误报处理**：`<div>`、`Map<String, Object>`、`<https://…>`、脚注 `[^1]` 均不会误判为占位——这是 2026-10-08 那轮修复的产物，此前干净产物会被判退 2。

### 已知限制（用之前必须知道）

| 限制 | 后果 | 缓解 |
|---|---|---|
| 只做**子串存在**判定，不校验顺序与层级 | 十节标题写在正文里也算通过；章节为空也能过 | 靠第二棒 requirement-reviewer 做内容评审 |
| **不校验**"本期不做"是否真有反例条目 | 写了标题没写内容，仍退 0 | 人工过 checklist（SKILL.md 流转门禁） |
| **不校验** FR 编号连续性与 P0 覆盖 | 编号跳号不影响退出码 | 同上 |
| 验收标准只要求存在该章节 | 形容词仍能过关 | 第二棒七维度评审 |
| 未做编码探测 | 非 UTF-8 文件可能抛异常而非给出可读错误 | 统一用 UTF-8 保存 |

**定位**：它是"结构闸门"，不是"质量闸门"。结构不齐一定拦得住；质量不行要靠第一棒自身克制与第二棒评审。

## 5. 运行环境

- Python ≥ 3.9，仅标准库（`re`/`sys`/`pathlib`）。
- 跨平台，无路径硬编码；产物路径从 CWD 解析，可传绝对路径。
- **WORKDIR 与 CWD 分离**：脚本路径与产物路径各自独立解析。整套部署时 CWD 在仓库根、产物参数写 `01-prd.md`；产物放在别处就传绝对路径，CWD 仍留在仓库根。

## 6. 能力边界

**能做**：

- 从零收敛需求，产出十节齐全的 PRD；
- 把口头约束转成可判定的验收标准；
- 显式划出"本期不做"；
- 标注假设与待确认项，而不是编造。

**不能做**（越界即被第二棒打回）：

- 技术选型、框架、数据库、加密算法；
- 界面布局与视觉方案（属第三、四棒）；
- 数据表结构（属第五棒）；
- 商业可行性判断、竞品分析、定价；
- 替用户决定做不做。

**边界判据**：写成"系统应该做到什么"归本棒；写成"代码应该怎么敲"归第七棒。

## 7. 设计取舍

| 选择 | 为什么不选另一条路 |
|---|---|
| 十节**固定标题**、字串硬匹配 | 自由结构无法机器校验。代价是模板僵化，收益是下游能按位置取字段 |
| 追问**硬上限 3 轮** | 不设上限时，Agent 会陷入无限澄清，项目卡在第一棒。代价是可能带着假设往下走，故强制标注「假设待确认」 |
| 占位符**判为不通过**而非警告 | 占位符一旦放行，下游会把 `[待补充]` 当真实需求实现。这条踩过坑，故收紧到必须清零 |
| 只查结构不查语义 | 语义判定必然误报，误报会让使用者绕过门禁。宁可漏，不可误 |

---

## 8. 优缺点

**优点**

- 零依赖，拷走目录即可跑，成本极低；
- 把"没说清"变成可机器发现的失败，而不是上线后才发现；
- 假设显式化，下游能看出哪里是猜的；
- 与下游编号契约（NFR-01）打通，减少重复抄写。

**缺点与缓解**

| 缺点 | 影响 | 缓解 |
|---|---|---|
| 结构闸门宽松，空章节能过 | 形式合规但内容空洞 | 第二棒七维度评审 + 人过 checklist |
| 十节模板对极小需求偏重 | 一个改文案的需求也要写十节 | 小改动不必进流水线；单棒可跳过 |
| 3 轮上限可能逼出假设 | 假设错了要返工 | 假设统一带「假设待确认」前缀，第二棒必查 |
| 不校验编号连续性 | 下游引用可能指向不存在的 FR | 第七棒落实说明需回写编号，断号会暴露 |

## 9. 失败模式与处置

| 现象 | 根因 | 处置 |
|---|---|---|
| 退 2 但肉眼看不出占位符 | 正文有 `【】` 或未闭合尖括号；或含"待补充"字样 | 脚本会打印命中类型与前三处原文，按提示定位 |
| 退 2 且报"尖括号占位" | 写了自己发明的泛型或未闭合标签 | 改用反引号包代码片段 |
| 连续 3 次同项失败 | 判据与产物长期不匹配 | 停止重试，出《门禁阻塞报告》：失败项原文 / 三次修改 / 误报还是缺陷 / 三个选项（放宽判据、人工补内容、标记风险放行） |
| 文档越改越乱 | 整篇重生成 | 定点修补：只重写失败项所在小节，其余原样保留 |

**禁止**：为让退出码变 0 而删改校验脚本，或把失败项文字改写掉规避匹配。

## 10. 与相邻技能的职责交界

| 邻棒 | 交界线 |
|---|---|
| requirement-reviewer（02） | 本棒保证"结构齐 + 假设显式"；02 判"能不能执行"，给 YES/NO，最多打回 2 次 |
| prototype-designer（03） | 本棒只写到"界面上应呈现什么"，不写布局；03 才画线框 |
| software-developer（07） | 本棒写要求（NFR-01 列表 2 秒内返回），07 写实现并在 README 回写编号 |
