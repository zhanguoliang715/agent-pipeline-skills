# 需求可执行性评审清单
> 配套 SKILL：requirement-reviewer（具体版本见该 SKILL.md 的 version 字段，不在此写死）
> 本文件版本：1.0.2

> 七大维度逐项过。任一"阻断项"命中，结论 = NO。

## 1. 完整性
- [ ] 有背景与量化目标
- [ ] 目标用户与场景明确
- [ ] 所有功能都有编号、无遗漏
- [ ] 主流程 + 至少一条异常分支
- 阻断项：核心功能缺失、流程跳步到无法理解

## 2. 可执行性（程序员能否直接开工）
- [ ] 每条需求描述的是"用户能做什么"，没有跳票到"用什么技术实现"
- [ ] 没有前后矛盾的需求
- [ ] 术语统一，同一个东西不出现多个名字
- 阻断项：关键功能只写了概念、没写具体行为

## 3. 边界清晰度
- [ ] 明确列出"本期不做什么"
- [ ] MVP 范围与 P1/P2 划分清楚
- 阻断项：**完全没有写"本期不做什么"**（只要写了，哪怕写得粗略也不算阻断；写得含糊、能被理解成多种做法，记为"存疑/建议"，不打回）

## 4. 验收标准可测性（测试能否直接写用例）
- [ ] 每条 FR 有验收标准
- [ ] 标准可客观判定（出现"友好/流畅/美观/快速"= 不可测）
- [ ] 覆盖正常 + 异常 + 边界
- 阻断项：任何一条 FR 验收标准缺失或不可测

## 5. 技术可行性风险
- [ ] 没有明显与现有系统能力冲突
- [ ] 没有依赖一个不存在或未确认的外部接口
- [ ] 工作量与目标工期无数量级冲突
- 阻断项：需求在已知条件下无法实现，或关键技术未经验证

## 6. 依赖、合规与安全
- [ ] 第三方账号/数据/接口依赖已列明且有人负责
- [ ] 涉及用户隐私/支付/权限的部分有基本要求
- 阻断项：触碰合规红线（如未声明的数据收集）却无任何说明

## 7. 跨文档一致性（功能清单 ↔ 范围边界 ↔ 验收标准 ↔ 下游口径）
- [ ] 功能清单里出现的每个 FR 编号，在"范围边界"里都有归属：列入"本期做"，或明确写进"本期不做"
- [ ] 验收标准覆盖的功能集合与功能清单一致：清单里的功能没有漏验收，验收里没有清单外的功能
- [ ] 下游交付口径一致：02 评审结论、04 测试范围、README 实现说明对每个 FR 的说法必须与 PRD 一致——PRD 范围边界没有排除的功能，下游产物不得出现"不实现"的口径
- 阻断项：功能清单与范围边界矛盾（某功能标 P0 在清单里、范围边界却排除且无说明）；验收标准与功能清单集合不一致

---

## 严重程度定义
- **阻断（必须改完再走）**：不改就开工，必然返工或做废。
- **建议（可带着走）**：不阻断开发，但应记录为已知风险，开发时留意。
